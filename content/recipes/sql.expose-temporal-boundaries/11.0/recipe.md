# Read row validity through ordinary entity properties

## Goal

Read SQL Server temporal history using database-generated CLR period properties, without treating those boundaries as user-editable dates. BeaconWatch keeps a name and an offset-bearing observation time for each navigation beacon. Its audit report needs both the history of renamed beacons and consistent hour buckets.

SQL Server temporal columns are generated by the database and cannot be updated by users. EF10 uses shadow period properties; EF11 can map them to CLR properties with private setters. Private setters express intent; SQL Server enforces the write restriction.

## Older approach — .NET10 / EF10

EF10's shadow period properties remain a valid way to project history. Parameterized SQL keeps time conversions and DATETRUNC on the database without requiring the newer LINQ translations. Both approaches solve the same reporting goal. This is a previous-release comparison, not a supported target10 edition or a new foundation.

## Migration

1. Choose one complete release-specific project and install its pinned SDK/runtime. Restore packages and retain the generated lock file.
2. Arrange an empty disposable SQL Server2025 database at compatibility170. Provide PLAYBOOK_SQL_CONNECTION_STRING only to the process. The sample uses EnsureCreated; it is not a migration strategy for an existing database.
3. Build and run the project in Release. It creates dbo.Beacons and its temporal history, inserts an observation, renames it and verifies both versions. Run once per fresh database.
4. For existing applications, map HasPeriodStart/HasPeriodEnd to the intended CLR properties when upgrading to EF11. Preserve existing column names and history configuration; inspect migration output before applying anything.
5. Keep reporting expressions inside IQueryable until execution. Choose UTC, a fixed offset or a deliberate server-local convention before grouping. Keep the EF10 parameterized SQL route where it fits the application.

## Constraints

SQL Server temporal columns are generated by the database and cannot be updated by users. EF10 uses shadow period properties; EF11 can map them to CLR properties with private setters. Private setters express intent; SQL Server enforces the write restriction.

The generated periods represent SQL Server transaction time in UTC, not the observation timestamp or client clock. CLR values materialized as DateTime do not automatically carry a UTC Kind. An hour bucket retains its offset; normalize to the intended reporting offset before grouping observations with different offsets. Do not call provider-only DateTrunc on in-memory collections.

No browser, rendering mode or workload is required. The EF11 sample requires net11.0 and C#15 as declared; no EF11-on-net10 route is offered. Stable API guidance is prepared with RC2 artifacts and still requires GA reconciliation. No experimental opt-in is used.
