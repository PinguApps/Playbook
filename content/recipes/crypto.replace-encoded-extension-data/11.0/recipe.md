# Update decoded certificate extension state through supported APIs

## Goal

A laboratory inspector replaces a certificate's Basic Constraints input after it
has already displayed the decoded fields. Keep the bytes, certificate-authority
flag, optional path length and Critical flag coherent. This updates an extension
object; it does not modify or re-sign a certificate that contains that extension.

## Older approach

The .NET10 setter compiles, but assigning new bytes cannot invalidate this derived
type's decoded cache. The laboratory first reads an end-entity extension, then
assigns bytes representing a CA with path length2. RawData changes; the displayed
fields still describe the old end entity. Critical also remains its original value.

{{snippet:older}}

This is a reproduced failure, not a safe update pattern. Typed construction and
CopyFrom already work on .NET10 and remain valid older solutions. The .NET11
change adds SYSLIB0065 specifically to the setter; the getter remains available.
Suppressing the diagnostic does not make the derived cache coherent.

## Newer approach

Prefer a replacement instance and pass the desired Critical value explicitly.
Where callers must retain the object identity, use the derived CopyFrom override.

{{snippet:newer}}

Both methods accept an incoming `X509BasicConstraintsExtension`. The constructor
chooses that decoded type and takes Critical from its explicit argument. For this
type, CopyFrom invalidates its decoded cache; the inherited X509Extension method
copies OID, bytes and Critical from an X509Extension input. Plain AsnEncodedData
is rejected with ArgumentException. Do not generalize these copy rules to every
derived ASN.1 type, or pass unrelated extension bytes under the wrong OID.

## Migration

1. Find writes to RawData separately from reads. Identify the actual extension
   type and its OID; this example is Basic Constraints, OID2.5.29.19.
2. Obtain the new encoded input and its intended Critical value. Create the
   appropriate incoming typed extension; these samples use distinct valid
   end-entity and CA/path2 inputs, generated by the typed Boolean constructor.
3. Replace the inspector's object with `ExtensionUpdate.Replace(incoming)` when
   reference identity is unnecessary. If identity must remain, call
   `ExtensionUpdate.Mutate(current, incoming)` instead.
4. Read the decoded properties at the validation boundary and handle
   CryptographicException before using them. In the measured constructor and
   CopyFrom paths, malformed bytes are stored successfully and fail when a decoded
   property is accessed. Construction alone does not validate the encoding.
5. Check raw bytes, OID, Critical and all decoded fields after both directions of
   an update. Build the newer consumer with warnings as errors, and retain
   getter-only code without a diagnostic suppression. Use a copied byte snapshot
   for read-only inspection; never mutate the array returned by RawData as an
   alternative update mechanism.

## Constraints

The current console sample targets net11.0 in C#15 mode and uses framework APIs
only. No NuGet package, native fixture, network, workload, provider, rendering mode
or experimental opt-in is needed. Application prerequisites are the .NET11
runtime/reference family; exact SDK pins below describe verification. The update
choices also execute on .NET10. This new catalogue guide has only target11: the
older consumer is comparison evidence, preserving the exact eight foundations.

The check covers one derived type on Windows x64 CoreCLR JIT. It makes no claim
about every ASN.1 subclass, other execution engines/platforms, certificate trust,
signature validation or final .NET11 GA. Critical is an extension-processing
attribute, not a substitute for checking the extension's decoded meaning.

## Evidence

`eng/Record-CertificateLinks.ps1 -VerifySources` records SDK10.0.402/C#14 with
reference/runtime10.0.13, and SDK11.0.100-rc.2.26504.105/C#15 with reference/runtime
11RC2. Compiler, reference and CoreLib identities/hashes, no resolved dependencies,
exact commands, input hashes and observed output are saved in the existing
sample-evidence records. Sources are hash-checked against the bounded audit and
qualified X509Extension implementation.

The older run reproduces stale fields with new raw bytes. Both runs verify typed
construction and CopyFrom, raw bytes/OID, Critical true then false, all decoded
fields, malformed-input failure at the actual decode boundary, plain
AsnEncodedData rejection and getter-only compilation. A separate current-target
project compiles the unchanged old setter with warnings as errors and must fail
with SYSLIB0065 alone; it uses no suppression. The supported newer project builds
with zero warnings/errors. The ordinary installed artifact returns complete
canonical Markdown, applicability and fresh records offline. RC proof leaves
PIN-959/PIN-962 and existing Human gates open.
