# Publishing workflow permission contract

## Reproduced failure

[Publish Release Draft run 40232758376](https://github.com/PinguApps/Playbook/actions/runs/40232758376)
at `8f3ff4f819b839af96a966bf853305c87d74edd1` completed with
`startup_failure` and zero jobs. Its annotation identifies the reusable call at
`.github/workflows/publish-release-draft.yml:52`: the nested verification job
requests `actions: read`, but its caller allows `actions: none`.

The new YAML contract check reproduced that mismatch before the fix:

```text
publish-release-draft.publish_packages -> publish.verify: requests actions: read, caller allows none
```

Adding `actions: read` to the existing `publish_packages` job permissions fixes
the ceiling passed through `publish.yml` to `_run-tests.yml`.
[GitHub's nested-workflow rules](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations#access-and-permissions-for-nested-workflows)
permit permissions to stay the same or become more restrictive down the chain.
Job conditions do not bypass startup validation.

## Paths and regression protection

`eng/Test-Renovate.mjs` uses the YAML parser already shipped with the pinned
Renovate installation. It checks the actual local reusable calls and each
callee job's requested permissions:

- Release-draft dispatch/schedule → package publication → verification.
- Direct published release and manual tagged publication → verification.
- Pull-request/manual validation → verification.

The checks also retain the reviewed permission maps: verification has
`contents: read`, `actions: read`, `checks: write` and `pull-requests: write`;
only the publishing job and its reusable caller request `id-token: write`.
The direct publication workflow retains its read-only default.
Both existing weekly publication conditions remain checked and unchanged.

The existing policy wrapper runs these checks on workflow/engineering changes
in PR validation and on every full/manual validation. No dependencies, Action
references, automated update permissions, root consumers or sample baselines
changed; `renovate.json` needs no new permissions.

## Local verification

The consumer inventory and strict Renovate configuration checks passed, followed
by the workflow contract and policy checks: 541 extracted dependencies and 498
protected sample entries. The local run reused an existing Renovate 44.172.1
installation; the normal wrapper can prepare that same pinned tool. Process,
user and machine PATH values were unchanged.

`eng/Test-Smoke.ps1` also passed: both maintained .NET 10 consumers built with
zero warnings/errors, the actual tool was packed and installed, and exactly one
MCP smoke scenario passed (zero failures/skips). This is local package evidence,
separate from the hosted publication jobs that deliberately did not execute.

Run from any PowerShell 7 working directory, with Git and network access for
policy-tool setup and shared-preset resolution:

```powershell
Set-Location -LiteralPath 'V:\_worktrees\Playbook\t3-0ec533da'
& ./eng/Test-DependencyPolicy.ps1
& ./eng/Test-Renovate.ps1
```

Expect the consumer-inventory, workflow-permission and Renovate-policy `PASS`
summaries, with strict configuration validation succeeding. The wrapper prepares
its pinned tools without changing PATH. These commands check configuration;
they do not publish or exchange a NuGet identity token.

## Hosted verification

[Branch dispatch 40242139836](https://github.com/PinguApps/Playbook/actions/runs/40242139836)
at `93c2ad8450bb0050b4dbec6cd8975342458c8069` completed with conclusion
`skipped`, rather than `startup_failure`. GitHub recorded both referenced
workflows (`publish.yml` and `_run-tests.yml`) at that exact commit. The jobs API
returned two completed jobs, both `skipped`: `publish_draft` and
`publish_packages`, with no steps executed. This establishes GitHub accepted
the real nested permission composition under the existing closed activation gate.

Repository variables were empty. The releases API showed only draft `v1.0.0`
before and after dispatch, with no published stable release. Neither the
activation variable nor any release, secret or NuGet policy was changed.

Inspect the recorded hosted result without dispatching another run:

```powershell
Set-Location -LiteralPath 'V:\_worktrees\Playbook\t3-0ec533da'
$gh = (Get-Command gh -CommandType Application | Select-Object -First 1).Source
& $gh run view 40242139836 --repo PinguApps/Playbook
& $gh api repos/PinguApps/Playbook/actions/runs/40242139836/jobs `
  --jq '.jobs[] | {name,status,conclusion}'
```

Expected: both jobs are skipped. No package verification runner, NuGet login,
OIDC token exchange or publication executed. Those are deliberate verification
limits; this run proves startup acceptance, not successful authentication or a
release-ready package. NuGet trusted publishing remains owner-controlled and
unconfigured for this task. Existing release/channel and exact-artifact/hash
safeguards are unchanged.
