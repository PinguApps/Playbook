# PIN-670: combined discovery filters and paging

`list_recipes` now combines optional area, language and keyword filters with release selection, explicit shared/neutral applicability and stable paging. Exactly two read-only tools remain; success responses preserve complete structured/JSON-text equality. Existing recipe IDs and ordinary catalogue content remain unchanged.

## Acceptance evidence

1. **Combined filters:** area/language sets use OR and filter types use AND. Omitted/empty sets mean all. Shared inclusion defaults true, broadens area matching only through per-route `sharedAreas`, and can be disabled. Different direct/shared areas, duplicate area matches, explicit older targets and all-term queries are exercised through the real installed fixture package.
2. **Language and applicability safety:** C# programming examples and C#-specific `LangVersion` XML remain non-neutral. Explicitly neutral `TargetFramework` XML uses empty example languages, a visible `languageNeutral` flag and per-route `neutralLanguages`. An F# filter returns only explicitly applicable neutral configuration. Unrelated Windows guidance is excluded from web/framework filters. A split-route case proves that area and language conditions from different routes cannot combine into a false match; summaries retain only matching routes. Experimental status and opt-ins stay visible. Content generation rejects source falsely labelled neutral and neutral-language declarations on programming recipes.
3. **Deterministic discovery:** all nonblank whitespace-separated terms must occur case-insensitively in title, goal, tags or API names. The combined request uses terms from all four fields. Stable ordinal IDs precede paging; default limit 20, maximum 50, total/offset/limit and nullable next offset are verified with 53 synthetic identities, exact traversal, a repeated first page, maximum-size page and an offset beyond the total (including `int.MaxValue`). Supported targets, areas and language-filter values remain discoverable; summaries contain applicability without Markdown implementations.
4. **Delivered boundary:** three focused scenarios extend the existing four. Every scenario installs the actual ordinary or unpublished fixture package from a fresh local-only feed/cache/store, outside the checkout, initializes stdio, calls MCP and shuts down cleanly with diagnostics on stderr. Tests distinguish correctable unknown area/language and invalid range failures from successful empty matches. Blank query behaves like omission. No production project reference or internal-method test seam is used.

## Inspect what an agent receives

Requires the pinned host SDK and Node 22.19 or later. Inspector's first invocation downloads the client; the server itself serves embedded guidance without fetching content. These tested commands call the real built server:

```powershell
Set-Location V:\_worktrees\Playbook\t3-ec3eebc7
dotnet build ./src/PinguApps.Playbook -c Release
$server = (Resolve-Path ./src/PinguApps.Playbook/bin/Release/net10.0/PinguApps.Playbook.dll).Path
$inspector = @('--yes', '@modelcontextprotocol/inspector@2.11.0', '--cli', '--format', 'json', '--quiet')
npx @inspector --method tools/list -- dotnet $server mcp
$list = npx @inspector --method tools/call --tool-name list_recipes --tool-arg 'targetVersion="10.0"' --tool-arg 'areas=["csharp"]' --tool-arg 'languages=["csharp"]' --tool-arg 'query=VALIDATION field' --tool-arg includeShared=false --tool-arg offset=0 --tool-arg limit=1 -- dotnet $server mcp | ConvertFrom-Json
$list.result.structuredContent | Format-List total, offset, limit, nextOffset
$list.result.structuredContent.recipes | Format-List id, title, goal, languageNeutral
$detail = npx @inspector --method tools/call --tool-name get_recipe --tool-arg id=csharp.validate-property-assignment --tool-arg 'targetVersion="10.0"' -- dotnet $server mcp | ConvertFrom-Json
$detail.result.structuredContent.recipe.markdown | Show-Markdown
$detail.result.structuredContent.recipe.applicability.routes | Format-List
```

Expect exactly `list_recipes` / `get_recipe`; discovery advertises all seven optional inputs. The filtered result contains the stable property ID, title and explanatory goal, `languageNeutral=false`, total 1, offset 0, limit 1 and no next offset. Detail displays both canonical implementations, migration/constraints and both explicit .NET 10 routes. All commands are short-lived; no background server needs cleanup. The [full walkthrough](../inspect-guidance.md#inspect-combined-filters-and-paging) also exercises successful zero matches and unknown-area corrections. Inspector 2.11.0 returned native exit 5 for the intentional tool error; parse its first stdout line and expect `isError=true`, `unknown_area`, rejected `blazro` and supported `csharp`.
