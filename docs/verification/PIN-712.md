## Inspect what an agent receives

Requires PowerShell 7.3+, SDK 10.0.402 and Node 22.19+. Inspector setup downloads its dependencies under ignored artifacts; the server retrieves embedded content offline. This follows [the Inspector walkthrough](../inspect-guidance.md), using the explicit Node entry point to avoid the npm executable-lookup failure recorded for PIN-711. Run from this checkout:

```powershell
& {
    $ErrorActionPreference = 'Stop'
    $PSNativeCommandUseErrorActionPreference = $true
    Set-Location -LiteralPath (git rev-parse --show-toplevel)
    dotnet build ./src/PinguApps.Playbook -c Release
    npm install --prefix ./artifacts/inspector-2.11.0 --no-audit --no-fund --package-lock=false @modelcontextprotocol/inspector@2.11.0
    $server = (Resolve-Path ./src/PinguApps.Playbook/bin/Release/net10.0/PinguApps.Playbook.dll).Path
    $inspector = (Resolve-Path ./artifacts/inspector-2.11.0/node_modules/@modelcontextprotocol/inspector/clients/launcher/build/index.js).Path
    $cli = @('--cli', '--format', 'json', '--quiet')
    node $inspector @cli --method tools/list -- dotnet $server mcp
    foreach ($target in @('10.0', '11.0')) {
        $targetArg = 'targetVersion="' + $target + '"'
        $catalogue = node $inspector @cli --method tools/call --tool-name list_recipes --tool-arg $targetArg --tool-arg query=collections -- dotnet $server mcp | ConvertFrom-Json
        $catalogue.result.structuredContent.recipes | Format-List id, title, goal
        foreach ($summary in $catalogue.result.structuredContent.recipes) {
            $response = node $inspector @cli --method tools/call --tool-name get_recipe --tool-arg "id=$($summary.id)" --tool-arg $targetArg -- dotnet $server mcp | ConvertFrom-Json
            $recipe = $response.result.structuredContent.recipe
            $recipe | Format-List id, edition, title, goal
            $recipe.markdown | Show-Markdown
            $recipe.applicability.routes | ConvertTo-Json -Depth 15
        }
    }
}
```

Expect one matching discovery entry for 10.0 (extension-property foundation) and three for 11.0. Each displays ID/title/goal, full rendered Markdown and target-specific applicability. The foundation keeps edition 10.0 and C# 14.0 at both targets; construction and indexers use edition 11.0 and C# 15.0. The 11.0 routes disclose RC2-only proof. No unresolved snippet tokens, missing body, unexpected target or absent constraints is acceptable. Each Inspector call shuts down its server automatically; no long-running service or cleanup is required.

## Prevent SDK first-run PATH registration

Pingu's failed inspection build led to a confirmed harness side effect: each fresh `DOTNET_CLI_HOME` allowed SDK first-run setup to register its temporary `.dotnet/tools` directory in the saved Windows user PATH. The existing `DOTNET_SKIP_FIRST_TIME_EXPERIENCE` variable is obsolete. The harness now explicitly sets `DOTNET_ADD_GLOBAL_TOOLS_TO_PATH=0` in every child environment, retains explicit `--tool-path` installation and launches the installed executable by absolute path. Every real install asserts unchanged process PATH and, on Windows, unchanged saved user/machine PATH. It reports differences without restoring shared settings.

Verification after the fix: Release test build passed with zero warnings/errors; all **15/15** installed scenarios passed against the existing ordinary/fixture packages. A separate **1/1 HostSmoke** run launched the compiled test executable with no inherited `DOTNET_ADD_GLOBAL_TOOLS_TO_PATH` setting, proving the harness supplies its own suppression for a real fresh-home installation. Exact process/user/machine PATH snapshots matched before and after both runs. Existing polluted PATH entries were left unchanged. The global `C:\Users\pingu\.codex\AGENTS.md` was updated separately at Pingu's request to prohibit direct and indirect PATH changes at every scope and require first-run suppression and saved-PATH checks.
