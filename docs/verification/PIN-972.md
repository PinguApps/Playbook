# PIN-972: requirements and verification baselines

Applicability routes now put actual application conditions under `requirements` and label their `usage` as `primary` or `optional-alternative`. Version requirements carry `name`, `version`, `match` (`release-family` or `exact`) and a source-supported `reason`. Families are bounded major.minor declarations, not inferred minima or future compatibility. Necessary exact package/workload/SDK pins remain representable; assets, providers, platform/rendering restrictions, experimental opt-ins and stability limits remain explicit.

The primary property route is .NET 10 runtime/SDK family with C# 14 mode. Its SDK 11 alternative keeps the .NET 10 target/runtime and C# 14. Introduction stays `10.0`, independently of a selected `11.0` target. The .NET 11 target and alternative disclose RC-only execution and pending GA reconciliation. Exact sample pins stay in the existing PIN-672 records, labelled `role: verification-baseline`; no input identities, commands, hashes or freshness semantics were changed. Runtime versions remain the actual measured `Runtime: .NET ...` output, not an inferred SDK host runtime.

The incompatible response shape is classified `major`; all packages used here are unpublished local development artifacts.

Actual results on 19 October 2026: `Verify.ps1 -ReleaseReady` passed all four real sample build/execution paths, 16 negative content cases, unchanged/stale evidence checks, real pack rejection gates and nine installed-MCP scenarios on Windows (.NET 10.0.13). Release builds had zero warnings/errors. The same ordinary/fixture packages passed all nine scenarios in Linux Docker (.NET 10.0.12) with `--network none` and no checkout mounted. Formatting and whitespace checks passed. Ordinary package SHA-256: `1e8a44cf33a031dfca8325fa8e7b7da1d3ee580e53178684b3557dddde6425e5`.

The Inspector 2.11.0 block below ran successfully against the built server and displayed discovery ID/title/goal, both requirements routes, full Markdown, exact evidence and .NET 11 RC limitations. The new installed scenario first failed against the previous package's missing route labels, then passed with the new contract. Saved sample records and their measured outputs remain unchanged; this run also recompiled/re-executed the samples without pretending their historical records were newly captured. Only process-scoped PATH additions were used. CI/review outcomes are recorded in the PR and Linear handoff.

## Acceptance coverage

1. Authored JSON, schema, generator, typed output schemas, discovery and full detail all separate requirements from test evidence. Installed tests compare the complete structured result with its JSON-text fallback.
2. Official field/language-versioning and SDK backwards-targeting references justify bounded requirements. Generation rejects prose requirements, malformed family pins and contradictory SDK/language evidence. The unpublished fixture preserves explicit exact pins and package/workload/provider/asset/rendering/experimental conditions without asserting those synthetic dependencies were installed or executed.
3. The ordinary package scenario checks the primary .NET 10 route first, absence of .NET 11 in its requirements, the optional SDK 11 choice, unchanged introduction, exact evidence and RC disclosures on the .NET 11 target.
4. Existing evidence remains unchanged and reusable. Freshness fixtures still reject changed source/SDK/dependency/toolchain inputs, missing compilation and mocks; release pack still rejects pending Human proof.
5. Real sample compilation/execution, build/pack rejection gates and installed-package scenarios exercise the contract. The Inspector example below displays the real built server's discovery, Markdown, applicability and baselines. Broader contributor/client setup remains PIN-674/PIN-675 work.

## Inspect what an agent receives

Requires PowerShell 7, SDK 10.0.402 and Node 22.19+. Inspector downloads its client on first use; the built server serves embedded content offline. The .NET 9/11 SDKs are needed to rerun the comparison samples, not to retrieve guidance. Every Inspector call initializes and shuts down its server automatically.

```powershell
Set-Location V:\_worktrees\Playbook\t3-90af328d
dotnet build ./src/PinguApps.Playbook -c Release
$server = (Resolve-Path ./src/PinguApps.Playbook/bin/Release/net10.0/PinguApps.Playbook.dll).Path
$inspector = @('--yes', '@modelcontextprotocol/inspector@2.11.0', '--cli', '--format', 'json', '--quiet')

$list = npx @inspector --method tools/call --tool-name list_recipes --tool-arg 'targetVersion="10.0"' -- dotnet $server mcp | ConvertFrom-Json
$list.result.structuredContent.recipes | Format-List id, title, goal
$list.result.structuredContent.recipes[0].applicability.routes | ForEach-Object {
  $_ | Format-List target, usage, conditional, evidenceSamples
  $_.requirements | ConvertTo-Json -Depth 10
}

$detail = npx @inspector --method tools/call --tool-name get_recipe --tool-arg id=csharp.validate-property-assignment --tool-arg 'targetVersion="10.0"' -- dotnet $server mcp | ConvertFrom-Json
$recipe = $detail.result.structuredContent.recipe
$recipe.markdown | Show-Markdown
$recipe.applicability.routes | ConvertTo-Json -Depth 10
$recipe.evidence | Format-List role, sample, target, sdk, language, dependencies, workloads, nativeToolchains, command, freshness, output

$eleven = npx @inspector --method tools/call --tool-name get_recipe --tool-arg id=csharp.validate-property-assignment --tool-arg 'targetVersion="11.0"' -- dotnet $server mcp | ConvertFrom-Json
$eleven.result.structuredContent.recipe.applicability.routes[0].requirements.stabilityLimitations
$eleven.result.structuredContent.recipe.evidence | Where-Object target -eq net11.0 | Format-List role, target, sdk, language, output
```

Expect ID `csharp.validate-property-assignment`, reusable title/goal and complete warehouse examples. The first route has `usage=primary`, runtime/SDK `version=10.0, match=release-family` and C# `14.0`. Only the optional alternative has SDK family `11.0`; both target .NET 10. Evidence retains exact SDKs `10.0.402` and `11.0.100-rc.2.26504.105`, target `net10.0`, commands and measured .NET 10 execution. The final request selects `11.0` while retaining introduction `10.0`; it discloses RC artifacts and pending GA reconciliation. Missing requirements, an exact test SDK presented as the primary requirement, incomplete Markdown or a GA-tested claim is a failure.

The same inspection can target the installed tool by replacing `dotnet $server mcp` with `./artifacts/manual-tool/playbook.exe mcp` after the [local install steps](../contributing.md#inspect-the-development-package). No persistent environment variables, global tool installation or service data changes are needed. No server is left running.
