# PIN-971: explicit recipe targets and deliberate latest

Both tools require a nonnullable `targetVersion` string in their advertised schemas and reject missing, null, empty or whitespace-only values with `isError: true`, code `required_target` and a corrective message. A narrow MCP request filter handles omission before SDK argument binding, which otherwise hides its explanation behind a generic invocation error. Null and blank values use catalogue validation.

`latest` resolves from the numerically ordered target releases represented in embedded editions. It consults no network, installed SDK inventory or independently assumed current release. Success echoes `requestedTarget` (including the exact alias or `latest`), canonical `resolvedTarget` and retained `targetAssumed: false`. There is no shared target state. Existing filters, paging, applicability, edition selection, errors and complete structured/JSON-text responses remain covered.

## Acceptance coverage

1. **Required contract and runtime rejection:** the actual installed ordinary package advertises required string schemas without a null/default alternative; real stdio calls reject omitted/null/blank targets on both tools. The new scenarios first failed against the old package because the schemas were optional and omission succeeded.
2. **Explicit latest:** both tools select the numeric maximum of advertised catalogue targets and echo the explicit choice. The installed host runs on .NET 10 while the catalogue resolves `latest` to `11.0`. The contract fixture also proves that `latest` is catalogue-wide: detail fails for a recipe whose only applicable route is .NET 10, even though that recipe exists.
3. **Compatibility and independent calls:** retained aliases choose the appropriate .NET 10/11 editions; all meaningful applicability fields and structured/text equality remain checked. Consecutive list/get calls prove that discovery never supplies a missing target or overrides a later concrete older target. Fixture scenarios retain shared/neutral/combined filtering, 53-identity paging and known-incompatible failures.
4. **Agent guidance and documentation:** initialization instructions, both tool descriptions, target-parameter descriptions, the [companion instruction](../agent-instructions.md), README, spec and current planning contracts explain target-framework/project/global.json inspection, repeated explicit targets, deliberate exploratory/unknown-target `latest`, SDK-versus-target distinction and compatibility limits. The historical brief and PIN-669 evidence are marked superseded. Four-client setup remains outside this issue.
5. **Public compatibility:** making a formerly optional input mandatory is `major` under the existing independent package policy. The PR uses that classification. Development package version remains the unpublished `1.0.0-preview.1`; no publication or stable-version change is authorized.

## Inspect what an agent receives

Requires PowerShell 7, SDK 10.0.402 and Node 22.19+. Inspector downloads its client on first use; Playbook reads embedded guidance offline. The following uses the actual built server; the package scenarios above exercise the installed artifact. Each Inspector command initializes and closes its server automatically.

```powershell
Set-Location V:\_worktrees\Playbook\t3-85f8d35e
dotnet build ./src/PinguApps.Playbook -c Release
$server = (Resolve-Path ./src/PinguApps.Playbook/bin/Release/net10.0/PinguApps.Playbook.dll).Path
$inspector = @('--yes', '@modelcontextprotocol/inspector@2.11.0', '--cli', '--format', 'json', '--quiet')

$tools = npx @inspector --method tools/list -- dotnet $server mcp | ConvertFrom-Json
$tools.result.tools | ForEach-Object { $_ | Format-List name, description; $_.inputSchema | ConvertTo-Json -Depth 10 }
$list = npx @inspector --method tools/call --tool-name list_recipes --tool-arg targetVersion=latest -- dotnet $server mcp | ConvertFrom-Json
$list.result.structuredContent | Format-List requestedTarget, resolvedTarget, targetAssumed
$list.result.structuredContent.recipes | Format-List id, title, goal
$detail = npx @inspector --method tools/call --tool-name get_recipe --tool-arg id=csharp.validate-property-assignment --tool-arg targetVersion=latest -- dotnet $server mcp | ConvertFrom-Json
$detail.result.structuredContent | Format-List requestedTarget, resolvedTarget, targetAssumed
$detail.result.structuredContent.recipe.markdown | Show-Markdown
$detail.result.structuredContent.recipe.applicability.routes | Format-List

# A subsequent concrete older target still selects its retained edition.
$older = npx @inspector --method tools/call --tool-name get_recipe --tool-arg id=csharp.validate-property-assignment --tool-arg 'targetVersion="10.0"' -- dotnet $server mcp | ConvertFrom-Json
$older.result.structuredContent.recipe | Format-List id, edition, goal
$older.result.structuredContent.recipe.applicability.routes | Format-List
```

Expected: exactly two read-only tools, both requiring string `targetVersion`; `requestedTarget=latest`, `resolvedTarget=11.0`, `targetAssumed=False` on list/get; discovery shows stable ID `csharp.validate-property-assignment`, its reusable title and goal; detail includes full older/newer Markdown and .NET 11 applicability. The final `10.0` call selects edition `10.0` with both the baseline and conditional SDK 11 route. No domain content or stable recipe ID changes.

For omitted/null/blank rejection on both tools, run the [release-selection failure block](../inspect-guidance.md#inspect-release-selection-and-failures). Each result is `isError=True`, with parseable `required_target` and instructions to supply a release or deliberate `latest`. Inspector intentionally exits nonzero on these tool failures, so that block scopes native-command error handling around them. A generic invocation failure or successful omission is a regression.
