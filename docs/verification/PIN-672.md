# PIN-672: reusable sample evidence

Recipe detail now embeds committed evidence from each sample's `verification-evidence.json`. The record identifies the source commit (and whether capture included working changes), exact sample/target/SDK/language, SHA-256 input snapshot, build/execution commands, resolved dependencies, required workloads/native versions, authoring OS/architecture, SDK/workload inventory and actual output. The hashes identify the exact files even when `sourceDirty` is true. They are not a signature or a substitute for reviewing the contributor's claims.

`freshness: current` means the committed inputs matched during content generation and packing. It does not probe the installed consumer. Unrelated commits or documentation edits do not invalidate a record; changes to a relevant input or its set do. Ordinary build and `pack --no-build` both reject missing/stale compilation before producing a package. Refreshing evidence also changes embedded content, so rebuild before a subsequent `pack --no-build`.

## Author and refresh proof

Each sample has `verification.json`, validated against `eng/verification.schema.json`:

- `additionalInputs`: repository-relative files/directories outside the sample that affect verification, including linked code and the capture scripts. Declare imported build files, shared assets and referenced-project input directories transitively. The validator checks explicit static project includes/imports against this set; it rejects dynamic project includes rather than silently guessing their expansion.
- `buildArguments`: explicit `-p:Name=Value` build properties, including any native RID/platform configuration. Changing these invalidates proof.
- `dependencies`: exact resolved `name/version` entries, including transitive packages/projects. Dependency-bearing samples require a committed `packages.lock.json`; capture builds with locked restore. Generate/review that lock before capturing proof.
- `workloads`: required `id/manifest-version` entries as reported by `dotnet workload list`. Unused installed workloads are inventory, not requirements.
- `nativeToolchains`: required `name/version` entries, measured on the authoring machine. Supply these measured values to `-NativeToolchains`; the helper compares the declaration but does not discover or independently authenticate arbitrary native tools. Preserve the version commands/results in the evidence scope or a linked authoring report.

The snapshot automatically includes the sample directory (excluding `bin`, `obj` and evidence records), linked inputs declared above, and the nearest effective `Directory.Build.props`, `Directory.Build.targets`, `Directory.Packages.props`, `NuGet.Config` and `global.json`. A newly added local override or sample file therefore invalidates prior proof. List any further imported ancestors or nonstandard configuration in `additionalInputs`. Keep required source files out of generated/evidence exclusions. Repository text uses LF; hashes are over exact bytes.

The helper runs the build, checks the selected SDK and resolved dependency versions, optionally executes the resulting DLL, and writes a record only after successful commands and an unchanged before/after snapshot. Use `-Kind compile` for build-only evidence or `-Kind cross-compile` when an actual cross-compilation was performed; neither executes the DLL. Native authors can commit records from suitable machines using the same schema. Routine validation consumes those records without requiring the native SDK/workloads on CI. There is no native recurring matrix.

The evidence schema distinguishes `official-review`, `compile`, `cross-compile`, `mock`, `execution` and `compile-and-run`. Additional separately authored records can be named `*.evidence.json` and selected with the recipe evidence entry's repository-relative `record` field. At least one fresh compilation record is required for every declared sample. Official review, mocks and execution-only records cannot replace it. Compilation and cross-compilation never establish real execution or device/UI behavior; only claim the scope actually observed. The fixture's synthetic official-review classification is explicitly not real review evidence.

Every recipe declares `humanProof.status` (`not-required`, `pending` or `verified`) and `scope`. Keep targeted Human checks pending until performed, then record the result and traceable evidence in scope. Pending proof remains visible in incremental package detail. `pwsh ./eng/Verify.ps1 -ReleaseReady`, `Build-Content.ps1 -ReleaseReady` and `dotnet pack -p:PlaybookReleaseReady=true` reject it. The publishing workflow enables this gate before its exact artifact is handed to publication; normal PR validation permits pending targeted proof. This gate covers evidence, not the separate full-catalogue, GA, client and product-evaluation launch requirements.

## Inspect what an agent receives

Requires PowerShell 7, SDK 10.0.402 and Node 22.19+. Saved compilation records allow this path without installing sample SDKs or native workloads. Adapt only the checkout path when using another machine. These commands install into a new temporary directory with a local-only package source/cache; they do not change global tools. Inspector downloads its own client online; guidance comes from the package.

```powershell
Set-Location V:\_worktrees\Playbook\t3-c6631afe
dotnet build ./src/PinguApps.Playbook -c Release
dotnet pack ./src/PinguApps.Playbook -c Release --no-build -p:PackageVersion=1.0.0-preview.1 --output ./artifacts/inspection-package
$inspection = Join-Path ([IO.Path]::GetTempPath()) ("playbook-inspect-" + [guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $inspection | Out-Null
$feed = (Resolve-Path ./artifacts/inspection-package).Path
$escapedFeed = [Security.SecurityElement]::Escape($feed)
"<configuration><packageSources><clear/><add key='local' value='$escapedFeed'/></packageSources></configuration>" | Set-Content (Join-Path $inspection 'NuGet.Config')
$previousPackages = $env:NUGET_PACKAGES
try {
  $env:NUGET_PACKAGES = Join-Path $inspection 'cache'
  dotnet tool install PinguApps.Playbook --version 1.0.0-preview.1 --tool-path (Join-Path $inspection 'tool') --configfile (Join-Path $inspection 'NuGet.Config')
  $server = Join-Path $inspection 'tool/playbook.exe'
  $inspector = @('--yes', '@modelcontextprotocol/inspector@2.11.0', '--cli', '--format', 'json', '--quiet')
  npx @inspector --method tools/list -- $server mcp
  $catalogue = npx @inspector --method tools/call --tool-name list_recipes --tool-arg 'targetVersion="10.0"' -- $server mcp | ConvertFrom-Json
  $catalogue.result.structuredContent.recipes | Format-List id, title, goal
  $response = npx @inspector --method tools/call --tool-name get_recipe --tool-arg id=csharp.validate-property-assignment --tool-arg 'targetVersion="10.0"' -- $server mcp | ConvertFrom-Json
  $recipe = $response.result.structuredContent.recipe
  $recipe.markdown | Show-Markdown
  $recipe.applicability.routes | Format-List
  $recipe.evidence | Format-List kind, sample, target, sdk, language, command, scope, recordedAt, sourceCommit, sourceDirty, inputs, dependencies, workloads, nativeToolchains, host, freshness, output
  $recipe.humanProof | Format-List
}
finally { $env:NUGET_PACKAGES = $previousPackages }
```

Expect two read-only tools and the stable ID `csharp.validate-property-assignment`, titled **Normalize and validate properties with the C# field keyword**, with its reusable `goal`. Detail contains original older/newer Markdown, both .NET 10 routes and three `compile-and-run` records marked `current`: .NET 9 comparison, .NET 10 baseline and .NET 11 RC SDK targeting .NET 10. Exact runtime versions appear in output. Dependencies/required workloads/native toolchains are empty for these portable samples. `humanProof.status` is `not-required`. To inspect the .NET 11 record use target `11.0`; that evidence remains RC, not GA. Inspector closes each server automatically. Delete the uniquely named `$inspection` directory when finished.

See [the general Inspector walkthrough](../inspect-guidance.md) for aliases, applicability and error inspection. Structural checks cannot prove that a hand-authored evidence record is truthful or that all indirect build inputs were declared; review that closure and actual output during contribution. No native compile/execution, additional client or GA verification is claimed by this slice.
