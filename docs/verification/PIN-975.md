# PIN-975: recover from empty recipe discovery

## Outcome

Empty discovery adds a small optional `recovery` object with a reason, explanation, effective filters and at most one complete suggested `list_recipes` request. Existing requested/resolved targets, coverage and paging metadata remain visible. Nonempty pages have no recovery property and no response-size increase.

A zero total uses `no_matches`. When compatible candidates exist without keywords, the suggestion removes every keyword and resets offset to zero, retaining the original target selection (including aliases or deliberate `latest`), areas, languages, shared setting and limit. The agent chooses whether to run it. When the same non-keyword combination is empty, the suggestion is null; no target or compatibility change is proposed. Both explanations warn that no match is not proof a capability does not exist and point to coverage.

An empty page at or beyond a nonzero total uses `offset_out_of_range` and suggests offset zero while preserving keywords and other filters. It is not a zero-match result. Invalid filters/targets/ranges still return their corrective tool errors. Structured content and the complete JSON text fallback remain identical. Nothing fetches guidance, retries automatically or manufactures results. This optional additive response capability is `minor`; development packages remain unpublished.

See the [contract](../planning/tool-contract.md#empty-discovery-recovery-pin-975). Recovery uses one message, one effective-filter echo and at most one request. The representative ordinary recovery budget is 1,200 UTF-8 bytes, without truncation; arbitrary input lengths are not a universal fixed budget. Existing ordinary/default/maximum discovery budgets remain unchanged.

## Inspect what an agent receives

Requires PowerShell 7, SDK 10.0.402 and Node 22.19+. Inspector 2.11.0 may download on first use; the Playbook server uses only embedded offline content. No .NET 9/11 SDK is required to inspect guidance. Commands initialize and close real built-server connections automatically.

```powershell
Set-Location V:\_worktrees\Playbook\t3-3dac009b
dotnet build ./src/PinguApps.Playbook -c Release
$server = (Resolve-Path ./src/PinguApps.Playbook/bin/Release/net10.0/PinguApps.Playbook.dll).Path
$inspector = @('--yes', '@modelcontextprotocol/inspector@2.11.0', '--cli', '--format', 'json', '--quiet')

# The original all-term search is valid, but has no matches.
$empty = npx @inspector --method tools/call --tool-name list_recipes --tool-arg targetVersion=net10.0 --tool-arg 'areas=["csharp"]' --tool-arg 'languages=["csharp"]' --tool-arg 'query=field nonexistent-term' --tool-arg includeShared=false --tool-arg limit=1 -- dotnet $server mcp | ConvertFrom-Json
$empty.result.structuredContent | Format-List requestedTarget, resolvedTarget, total, recipes
$empty.result.structuredContent.coverage | Format-Table target, scope, complete, description -Wrap
$empty.result.structuredContent.recovery | ConvertTo-Json -Depth 10

# Deliberately choose the suggested request; execute its returned arguments unchanged.
$retry = $empty.result.structuredContent.recovery.suggestedRequest
$retryArgs = @()
foreach ($property in $retry.PSObject.Properties) {
  $retryArgs += '--tool-arg'
  $retryArgs += "$($property.Name)=$(ConvertTo-Json -InputObject $property.Value -Compress -Depth 10)"
}
$list = npx @inspector --method tools/call --tool-name list_recipes @retryArgs -- dotnet $server mcp | ConvertFrom-Json
$list.result.structuredContent.recipes | Format-List id, title, goal
$list.result.structuredContent.recipes.applicability | ConvertTo-Json -Depth 10

# Get complete instructions and requirements with the same explicit target.
$id = $list.result.structuredContent.recipes[0].id
$detail = npx @inspector --method tools/call --tool-name get_recipe --tool-arg "id=$id" --tool-arg "targetVersion=$($retry.targetVersion)" -- dotnet $server mcp | ConvertFrom-Json
$detail.result.structuredContent.recipe.markdown | Show-Markdown
$detail.result.structuredContent.recipe.applicability | ConvertTo-Json -Depth 10
```

Expect an initial successful `total=0`, no recipes, `requestedTarget=net10.0`, `resolvedTarget=10.0`, both incomplete coverage disclosures and `reason=no_matches`. The suggested request keeps `net10.0`, both `csharp` sets, `includeShared=false`, `limit=1`, sets `query=null` and `offset=0`. Running it returns `csharp.validate-property-assignment`, titled **Normalize and validate properties with the C# field keyword**, with a reusable `goal` explaining normalization/validation in property setters. Discovery retains compact separate primary/optional conditions; detail returns the full original warehouse Markdown and target-10 applicability (normal SDK 10 and optional SDK 11 routes, with RC limitations). Evidence pins do not require exact SDK installations. Missing filters, changed targets, missing detail or a claim of exhaustive absence is a failure.

The ordinary package has one stable C# goal, so no-safe-retry and multi-page cases use the separate unpublished fixture. That is contract evidence, not new shipped recipes, F#/native execution or comprehensive coverage. No real-agent usability exercise or GA verification is claimed.
