# PIN-974: concise discovery without hidden applicability

## Outcome and contract

Discovery keeps stable IDs, reusable titles/goals, selected edition/introduction, demonstrated or neutral languages, stability, supported filter values and deterministic paging. Its compact routes preserve separate choices, version names/values/matching semantics, framework/package/workload/assets/provider/platform/rendering restrictions, opt-ins, stability warnings and authored selection notes. Nothing is merged or truncated.

Full alternative routes, version reasons, detailed prerequisites/constraints, route sources/evidence links, exact verification baselines/commands, official sources and complete Markdown remain in `get_recipe`. Discovery and initialization explicitly require checking that detail before applying guidance. Both tools retain complete structured/JSON-text equality. No third tool or extra call for basic selection was added.

Every authored route now declares `selectionNotes`. Authors review free-text prerequisites/constraints for essential selection restrictions. The schema requires the declaration, but cannot prove its semantic completeness. Empty notes are valid only when structured conditions and warnings suffice. Experimental opt-ins and stability limitations are copied without omission; budgets never change runtime output.

This is an incompatible public response-shape change (`major`). Consumers reading detailed fields from discovery must retrieve them through `get_recipe`; absent discovery fields are not unrestricted conditions. Unpublished development packages remain `1.0.0-preview.1`. No release is performed.

## Inspect what an agent receives

Requires PowerShell 7, SDK 10.0.402 and Node 22.19+. Inspector is pinned to 2.11.0; its initial download is online. The server reads embedded offline content. No .NET 9/11 SDK is needed just to inspect it.

```powershell
Set-Location V:\_worktrees\Playbook\t3-33d73aa8
$powerShell = (Get-Process -Id $PID).Path
$env:PATH = "$(Split-Path $powerShell);$env:PATH" # This process and its children only.
dotnet build ./src/PinguApps.Playbook -c Release "-p:PowerShellExecutable=$powerShell"
$server = (Resolve-Path ./src/PinguApps.Playbook/bin/Release/net10.0/PinguApps.Playbook.dll).Path
$inspector = @('--yes', '@modelcontextprotocol/inspector@2.11.0', '--cli', '--format', 'json', '--quiet')

$tools = npx @inspector --method tools/list -- dotnet $server mcp | ConvertFrom-Json
$tools.result.tools | Format-List name, description
$list = npx @inspector --method tools/call --tool-name list_recipes --tool-arg 'targetVersion="10.0"' -- dotnet $server mcp | ConvertFrom-Json
$list.result.structuredContent.recipes | Format-List id, title, goal, edition, introducedIn
$list.result.structuredContent.recipes.applicability | ConvertTo-Json -Depth 10

$detail = npx @inspector --method tools/call --tool-name get_recipe --tool-arg id=csharp.validate-property-assignment --tool-arg 'targetVersion="10.0"' -- dotnet $server mcp | ConvertFrom-Json
$recipe = $detail.result.structuredContent.recipe
$recipe.markdown | Show-Markdown
$recipe.applicability | ConvertTo-Json -Depth 10
$recipe.evidence | Format-Table role, sample, target, sdk, language, freshness -Wrap
```

Expect `csharp.validate-property-assignment`, titled **Normalize and validate properties with the C# field keyword**, with a goal explaining when to use it. Edition/introduction stay `10.0`. Discovery shows separate runtime 10 / SDK 10 primary and runtime 10 / SDK 11 optional choices, C# 14, exact/family meaning, selection notes and the alternative's RC warning. It has no version `reason`, detailed prerequisites/constraints or route source/evidence links. Detail retains those fields and complete warehouse Markdown, including both canonical implementations, migration, initialization caveats and alternatives. Evidence pins are reproducibility baselines, not required installations. Missing safety warnings, mixed route requirements, missing detail or different structured/text content is a failure. Inspector initializes and closes each connection automatically.

## Build command correction

A user reported MSB3073/exit 9009 from the PR walkthrough while already running PowerShell 7. The original build invoked `pwsh` by name. Adding `$PSHOME` to PATH does not prove that a child command processor can resolve it. The exact user environment was not reproduced; the same missing-command failure was reproduced in a clean PowerShell 7 process with `pwsh` absent from PATH.

Build and pack now accept `PowerShellExecutable`, defaulting to `pwsh`. The walkthrough passes the current PowerShell 7 executable path explicitly; the executable's directory is also added to the invoking process's PATH for child scripts. The build and real `pack --no-build` succeeded with `pwsh` absent from PATH when given the explicit path. No persistent environment setting changes. Existing build validation and the default CI invocation are preserved. Post-fix validation passed all eleven installed-MCP scenarios using the rebuilt ordinary package and unchanged fixture, plus formatting and the corrected Inspector walkthrough. The initial repack test detected a version-label mismatch in the temporary test artifact; rebuilding with the matching preview version corrected that verification setup before the successful run.
